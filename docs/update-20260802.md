```

        │
        ▼ （如果执行 mvn package）

        │
        └── 读取 excludes 配置 → 跳过 lombok 依赖
        │
        ▼
生成的 jar 包中不包含 lombok，体积更小 ✅
```

## 三、UserService.java — 泛型补全

**文件路径：** [service/UserService.java#L1-L7](file:///c:/Users/27019/Desktop/测试文件夹/springDemo/src/main/java/com/example/springdemo/service/UserService.java#L1-L7)

### 完整代码

```java
package com.example.springdemo.service;

import com.baomidou.mybatisplus.spring.service.IService;
import com.example.springdemo.entity.User;

public interface UserService extends IService<User> {  // ← 新增 <User> 泛型
}
```

---

### 3.1 注解/接口解释

| 元素 | 所属包 | 作用 |
|------|--------|------|
| `IService<T>` | `com.baomidou.mybatisplus.spring.service` | MyBatis-Plus 提供的**通用 Service 层接口**，泛型 `T` 为实体类型；指定 `<User>` 后，接口中的 `getById/save/list/page` 等方法都绑定为 `User` 类型，编译期类型安全 |

### 3.2 错误写法 vs 正确写法

| 对比项 | 错误写法（之前） | 正确写法（现在） |
|--------|------------------|------------------|
| 代码 | `extends IService` | `extends IService<User>` |
| 泛型擦除 | T 被擦除为 `Object`，方法参数无类型约束 | T 固定为 `User`，强类型 |
| getById 返回 | `Object`，需强转 | 直接返回 `User`，无需强转 |
| 编译检查 | save(Object) 可传入任何对象，不安全 | save(User) 只能传入 User，编译期报错 |
| 对 ServiceImpl 影响 | 与 `ServiceImpl<Mapper,User>` 的泛型链断裂，可能触发协变冲突 | 泛型链闭合，`getBaseMapper()` 返回类型一致 |

---

### 3.3 为什么会导致 getBaseMapper() 冲突？

```
泛型链路断裂示意：

    IService                   ServiceImpl<UserMapper, User>
       │ （擦除为Object）                │ 返回值: UserMapper getBaseMapper()
       │                                 │
       └── UserService implements ───────┘
                        ↕ 类型不匹配！
            IService.getBaseMapper() 推断返回 ?
            ServiceImpl.getBaseMapper() 返回 UserMapper
            ↕ 两条父接口同方法签名、返回类型不兼容 → CONFLICT 报错！
```

### 4.4 类层次 + 泛型闭合链路

```
                    ┌──────────────────────────────┐
                    │    BaseMapper<User>          │
                    │    (UserMapper extends它)    │
                    └──────────────┬───────────────┘
                                   │
┌───────────────────┐     ┌───────▼──────────────────┐
│ IService<User>    │────▶│ ServiceImpl<             │
│ (接口层)          │     │   UserMapper,            │
│                   │     │   User                   │
└──────────┬────────┘     │   (已实现所有通用方法!)    │
           │              └──────────┬────────────────┘
           │ implements              │ extends
           ▼                         ▼
      ┌─────────────────────────────────────────┐
      │     UserServiceImpl                     │
      │     @Service → IOC容器可注入             │
      │     泛型闭合 → getBaseMapper() 返回一致  │
      │     → 无冲突，编译通过 ✅                  │
      └─────────────────────────────────────────┘
```

**关键：** 所有父接口/父类的泛型全部绑定到 `<UserMapper, User>` → `getBaseMapper()` 不论从哪条父链路推断，返回值都是 `UserMapper` → **方法签名协变兼容 → 无冲突**。

## 五、UserController.java — 三层架构改造 + 统一返回格式

**文件路径：** [controller/UserController.java](file:///c:/Users/27019/Desktop/测试文件夹/springDemo/src/main/java/com/example/springdemo/controller/UserController.java)

### 完整代码

```java
package com.example.springdemo.controller;

import com.baomidou.mybatisplus.core.conditions.query.LambdaQueryWrapper;
import com.baomidou.mybatisplus.core.conditions.update.LambdaUpdateWrapper;
import com.baomidou.mybatisplus.extension.plugins.pagination.Page;
import com.example.springdemo.common.Result;
import com.example.springdemo.entity.User;
import com.example.springdemo.mapper.UserMapper;
import com.example.springdemo.service.UserService;
import jakarta.annotation.Resource;
import org.springframework.boot.SpringApplication;
import org.springframework.boot.autoconfigure.SpringBootApplication;
import org.springframework.web.bind.annotation.*;

import java.util.List;

@RestController
@RequestMapping("/user")
public class UserController{

    // 旧：直接注入 Mapper（已注释）
    //@Resource
    //private UserMapper userMapper;

    // 新：注入 Service 层（三层架构规范）
    @Resource
    private UserService userService;

    // 1. 新增用户
    @PostMapping("/user")
    public Result save(@RequestBody User user) {
        return Result.success(userService.save(user));
    }

    // 2. 查询所有用户
    @GetMapping("/user")
    public Result getAll() {
        return Result.success(userService.list());
    }

    // 3. 根据ID查询用户
    @GetMapping("/user/{id}")
    public Result get(@PathVariable Integer id) {
        return Result.success(userService.getById(id));
    }

    // 4. 修改用户
    @PutMapping("/user/{id}")
    public Result update(@PathVariable Long id, @RequestBody User user) {
        return Result.success(userService.updateById(user));
    }

    // 5. 删除用户
    @DeleteMapping("/user/{id}")
    public Result delete(@PathVariable Long id) {
        return Result.success(userService.removeById(id));
    }

    // 6. 【新增】条件分页查询
    @GetMapping("/page")
    public Result findpage(
            @RequestParam(defaultValue = "1")  Integer pageNum,
            @RequestParam(defaultValue = "10") Integer pageSize,
            @RequestParam(defaultValue = "")   String name) {
        LambdaQueryWrapper<User> lambdaQueryWrapper = new LambdaQueryWrapper<>();
        if (name != null && !"".equals(name)) {
            lambdaQueryWrapper.eq(User::getName, name);
        }
        return Result.success(userService.page(new Page<>(pageNum, pageSize), lambdaQueryWrapper));
    }
}
```

---

### 5.1 核心改动一：从 UserMapper → UserService

| 对比项 | 旧：直接用 Mapper | 新：走 Service 层 |
|--------|-------------------|-------------------|
| 代码 | `@Resource UserMapper userMapper` | `@Resource UserService userService` |
| 调用 | `userMapper.selectXxx()` | `userService.xxx()` |
| 扩展性 | 业务逻辑只能写在 Controller，耦合高 | 业务逻辑集中在 Service，可复用、可加事务 |
| 事务支持 | Controller 加 @Transactional 不规范 | Service 层加 `@Transactional` 标准做法 |
| 代码复用 | 多个 Controller 同样逻辑只能复制 | Service 方法可被多个 Controller/Service 调用 |

---

### 5.2 核心改动二：返回值全部改为 Result

| 对比项 | 旧：String / Page 直接返回 | 新：Result 统一包装 |
|--------|-----------------------------|---------------------|
| 返回示例1 | `"用户新增成功"`（纯文本） | `{"code":200,"msg":"操作成功","data":true}`（标准JSON） |
| 返回示例2 | `Page<User>` 对象，结构不稳定 | `{"code":200,"msg":"操作成功","data":{"records":[...],"total":100}}` |
| 前端解析 | 每个接口格式不同，写N种解析逻辑 | 所有接口统一：先判断 code，再取 data |
| 与全局异常配合 | 正常返回文本 vs 异常返回{code,msg} → 格式不一致 | 正常/异常均返回 Result → 前端统一处理 |
